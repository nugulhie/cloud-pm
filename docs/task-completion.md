# 태스크 완료 처리와 YAML 자동 완료

## 직접 완료와 재개방

쓰기 권한이 있는 사용자는 PR/YAML 없이 `status:"done"`으로 직접 완료하고 다른 상태로 재개방할 수 있다. 웹의 상세 상태·보드 드래그·계층 보기 체크박스·일괄 상태 수정과 MCP의 `update_task`/`update_task_fields`가 같은 서비스를 사용한다. 기존 권한·revision·관계 검사는 유지하고 변경자·시각·이전/이후 상태를 이력에 남긴다.

부모와 하위 태스크 상태는 독립적이다. 하위가 완료되었다고 부모를 자동 완료하지 않으며 부모 완료가 하위 상태를 바꾸지도 않는다. 완료 개수는 하위 작업의 실제 상태를 집계한다.

PR 자동 완료는 아래 규칙으로 유지한다. 직접 재개방했더라도 기본 브랜치의 활성 PR 조건이 계속 충족되면 다음 동기화에서 다시 완료된다. PR 미충족/조회 실패로 이미 완료한 작업을 자동 재개방하지 않는다.

## 목적과 저장 위치

개발자는 태스크의 프로젝트·기능과 완료 조건을 YAML로 등록합니다. 서비스 이용 저장소의 `.cloud-pm/tasks/<task-id>.yaml`에 두고 코드와 함께 리뷰합니다. 이 저장소의 [예제](../examples/tasks/social-login.yaml)는 설명용이며 활성 태스크 설정이 아닙니다. YAML 파서와 완료 조건 평가기는 `src/completion/index.ts`에 구현되어 있습니다. `src/github/`와 CLI에서 기본 브랜치 YAML 수집 및 실제 PR 조회를 지원합니다. 수동·CLI 동기화에서 평가 근거를 DB에 저장하고 등록 태스크를 완료 처리합니다. 자동 스케줄 등록과 웹훅은 구현 전입니다.

## 초기 형식

`version: 1`, `task`, `project`, `feature`, `completion`을 필수로 둡니다. 프로젝트와 기능은 시스템에 등록된 식별자를 참조합니다. 태스크 식별자는 조직 내에서 유일하게 관리하며, 같은 태스크의 설정이 여러 곳에 등록되면 충돌을 표시하고 임의로 덮어쓰지 않습니다.

`completion`은 `all` 또는 `any` 중 하나를 사용합니다. 각 조건은 `pull_request`이며, `repository`는 `owner/repository`, `number`는 양의 정수, `state`는 `merged`, `target_branch`는 머지 대상 브랜치입니다. 초기 형식은 중첩 조합을 지원하지 않습니다. 빈 조건 목록, 알 수 없는 키, 중복 YAML 키, 지원하지 않는 버전은 검증 오류로 처리합니다.

## 평가 규칙

| 조건  | 충족                        | 미충족                                                        | 미확인                                  |
| ----- | --------------------------- | ------------------------------------------------------------- | --------------------------------------- |
| PR    | 지정한 대상 브랜치로 머지됨 | 조회 성공 후 열린 상태·머지 없이 종료·대상 브랜치 불일치 확인 | 권한 부족·조회 실패·존재 여부 확인 불가 |
| `all` | 모든 조건 충족              | 하나 이상 미충족                                              | 미충족 없이 미확인이 남음               |
| `any` | 하나 이상 충족              | 모든 조건 미충족                                              | 충족 없이 미확인이 남음                 |

유효한 설정의 조건이 충족되면 태스크를 `done`으로 전환합니다. 단순 참조 PR은 조건에 포함하지 않으며 QA·배포는 별도 상태로 표시합니다. 설정 오류와 조회 실패로 태스크를 완료 처리하지 않습니다. 취소된 태스크는 조건을 충족해도 자동 재활성화하지 않습니다. 완료 태스크는 조건 변경·revert로 자동 재개방하지 않습니다.

## 표시와 변경 이력

PM에게는 YAML 대신 “백엔드 머지 완료 / 프론트엔드 머지 대기”처럼 조건별 결과와 근거 링크를 제공합니다. 웹과 MCP는 동일한 검증·평가 서비스를 이용합니다. AI는 설정 작성을 보조할 수 있지만 확정된 조건을 임의로 바꾸지 않습니다.

설정의 저장소·경로·커밋 SHA, 조건 버전, 변경자, 평가 시각, 원본 조회 시각, PR 머지 시각을 기록합니다. 평가 기록은 덮어쓰지 않습니다. 임의 명령, 스크립트, 템플릿 실행은 지원하지 않습니다.

## 아직 정해야 할 정책

- 기본 브랜치 변경 시 설정을 다시 활성화하는 절차.
- 완료 후 조건 변경 또는 PR revert 시 재개방 여부.
- 여러 저장소에 걸친 설정의 등록 권한과 충돌 해결 절차.

초기 활성화 정책은 저장소의 기본 브랜치에 반영된 YAML만 유효 설정으로 읽는 것입니다. 설정을 읽은 커밋 SHA를 고정해 기록하며 feature 브랜치의 설정은 미리보기 검증에만 사용합니다. GitHub 설정 로더는 기본 브랜치 ref를 커밋 SHA로 고정하고 해당 SHA에서만 목록과 파일을 읽습니다.

평가기는 판정 결과만 반환합니다. 같은 설정 저장소 내 중복 태스크는 평가에서 제외합니다. 프로젝트·기능 존재 확인, 조회에 성공한 저장소 간 중복 검사, 평가 이력 저장과 `done` 전환은 공통 서비스가 수행합니다. 워크스페이스 조회·수정 권한은 적용하지만 사용자별 저장소 ACL은 구현 전입니다. GitHub 조회에는 제공된 토큰의 권한이 적용됩니다.

## 웹 YAML 초안과 활성 설정

태스크 편집 화면의 YAML은 작성용 초안입니다. 저장 시 식별자와 형식을 검증하지만 활성 완료 조건으로 사용하지 않습니다. 개발자가 저장소 기본 브랜치에 반영한 YAML이 원본입니다. 동기화 평가 기록에는 실제 적용한 조건·커밋 SHA를 보관합니다. 등록되지 않은 태스크, 프로젝트 범위 밖의 저장소·조건, 중복 설정은 완료 처리에서 제외합니다.

# 제품 및 설계 방향

## 확정된 요구사항

- PM이 조직의 여러 GitHub 저장소에 걸친 프로젝트 상황을 파악하는 것이 주 목적입니다.
- 개발자는 태스크를 관리하고 관련 이슈·PR·파일 변경을 확인할 수 있어야 합니다.
- 외부 AI 클라이언트에서 MCP로 기능을 사용할 수 있도록 인터페이스를 개방합니다.
- Next.js·TypeScript·PostgreSQL을 기본 기술 구성으로 사용합니다.
- PM 대시보드는 기능별 진행 현황과 개입이 필요한 항목을 함께 제공합니다.
- PM이 프로젝트의 기능과 목표를 등록하고, 개발자가 태스크에 관련 프로젝트와 기능을 등록합니다. AI는 관련 GitHub 이슈·PR 연결을 보조적으로 제안합니다.
- 태스크는 사용자가 직접 완료하거나 해당 기능을 구현한 PR의 머지 조건으로 자동 완료합니다. QA·배포 여부는 별도 정보로 표시합니다.
- 개발자는 저장소의 `.cloud-pm/tasks/`에 YAML로 프로젝트·기능 및 완료 조건을 정의합니다. 지정 PR의 머지 조건을 `all` 또는 `any`로 조합합니다. [완료 조건 명세](task-completion.md)를 참고하세요.

## 현재 구현의 ‘기능’과 GitHub 브랜치

현재 기능(`Feature`)은 프로젝트에 속한 태스크를 묶는 내부 관리 항목입니다. `id`, `project`, `name`, `goal`을 저장하며 GitHub 브랜치 이름이나 브랜치 수명과 연결하지 않습니다. 하나의 기능에 여러 저장소의 태스크와 PR을 연결할 수 있습니다. 기능 카드의 완료율은 등록된 비취소 태스크의 완료 비율이며, 기능의 인수 조건이나 배포 완료를 판정하는 별도 상태는 아직 없습니다.

사용자는 PR 없이 태스크를 직접 완료할 수 있습니다. 자동 완료는 개발자가 YAML에 지정한 구현 PR의 머지 조건으로 평가합니다. `feature/*` 브랜치라는 이름만으로 기능을 생성하거나 완료하지 않습니다. 기능을 사용자 가치 중심으로 제한할지, 기술 개선과 운영까지 포함한 작업 묶음으로 확장할지는 제품 용어와 집계 정책을 함께 확정할 사항입니다.

## 사용자별 화면

PM 화면은 프로젝트별 진행 작업, 주요 변경, 지연·차단 요인, 다음 행동이 필요한 항목을 우선 표시합니다. 개발자 화면은 담당 태스크, 상태 변경, 연결된 이슈·PR 및 리뷰 요청을 중심으로 구성합니다. 역할별 화면과 실제 접근 권한은 별도로 설계합니다.

## 프로젝트 구성과 기본 사용 흐름

프로젝트 아래 기능을 두고, 기능에 태스크와 여러 저장소의 이슈·PR을 연결합니다. 마일스톤은 일정 목표를 묶는 별도 개념으로 상세 모델을 추후 정의합니다.

1. PM이 프로젝트의 목표와 조회 대상 저장소를 등록합니다.
2. PM이 기능별 목표를 작성합니다. 담당자·목표일은 선택적으로 지정합니다.
3. 개발자가 태스크에 관련 프로젝트·기능과 구현 feature의 PR을 등록합니다. AI는 관련 이슈·PR 후보와 연결 이유를 보조적으로 제안합니다.
4. 개발자 또는 권한 있는 사용자가 후보를 승인·거절하거나 직접 연결합니다.
5. 승인된 연결을 기준으로 기능별 진행 현황을 집계하고, 미연결 후보는 별도로 표시합니다.
6. YAML에 등록한 feature PR의 머지 조건이 충족되면 태스크를 완료 처리합니다. 개발자는 진행 상태와 차단 사유를 보완하고, PM은 담당자 지정·우선순위 조정·후속 태스크 생성으로 이어갑니다.

AI가 제안한 연결과 사람이 확정한 연결을 구분합니다. 재분석 시 사람이 확정한 관계를 임의로 변경하지 않고, 거절한 후보는 새로운 근거 없이 반복 제안하지 않는 방향으로 설계합니다. 연결 및 해제 이력을 보존하고 같은 PR이 여러 기능에 연결되어도 프로젝트 집계에서는 중복 계산하지 않습니다.

## PM 대시보드 구성

상단에는 개입이 필요한 항목을, 본문에는 기능별 진행 현황을 표시합니다. 개입 항목을 선택하면 해당 기능·태스크와 근거로 이동합니다.

| 영역        | 표시 내용                                                    | 가능한 행동                                       |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------- |
| 개입 필요   | 담당자 미지정, 차단된 작업, 리뷰 대기, CI 실패, 기한 초과    | 담당자 지정, 기한·우선순위 조정, 후속 태스크 생성 |
| 기능별 현황 | 완료·진행·남은 작업, 담당자, 연결된 이슈·PR, 최근 변경       | 상세 조회, 태스크 추가, 연결 후보 검토            |
| 기능 상세   | 목표·완료 기준, 작업 간 의존 관계, 리뷰·CI 근거, 파일별 변경 | 연결 수정, 차단 사유 갱신, 완료 여부 확인         |

예시: 소셜 로그인 태스크의 구현 feature가 머지되면 태스크를 완료로 표시합니다. QA·배포 상태는 별도로 표시하며, 미완료 QA·배포 항목이 있다고 해당 태스크의 완료를 보류하지 않습니다. 별도 환경 설정 태스크의 담당자가 없다면 개입 필요 항목으로 표시합니다.

작업 단계와 주의 상태를 분리합니다. 예를 들어 `in_review`인 태스크가 정상 진행 중일 수도, 검토 지연 상태일 수도 있습니다. CI 실패나 리뷰 대기가 실제 일정 위험인지에 대한 해석은 관측 사실과 구분하고, 기한·대기 시간·의존 관계를 근거로 제시합니다. 위험 판정 임계값과 수동 조정 정책은 추후 확정합니다.

## 태스크 모델 제안

개발자가 태스크에 관련 프로젝트와 기능을 명시적으로 등록합니다. 제목, 설명, 담당자, 상태, 우선순위, 기한 및 관련 GitHub 항목을 가질 수 있습니다. 하나의 태스크가 여러 저장소의 이슈와 PR에 연결될 수 있도록 합니다.

초기 상태는 `backlog`, `ready`, `in_progress`, `in_review`, `done`, `canceled`를 제안합니다. 차단 여부와 차단 사유는 상태와 별도로 관리합니다. 해당 태스크의 기능을 구현한 feature의 머지를 확인하면 `done`으로 자동 전환합니다. 단순 참조 PR이나 머지 없이 닫힌 PR은 완료 근거로 사용하지 않습니다. 완료 근거인 PR과 머지 시각을 기록합니다.

feature의 머지는 구현 PR의 머지로 해석합니다. 완료를 결정하는 PR과 대상 브랜치는 개발자가 YAML에 지정하고 `all` 또는 `any`로 조합합니다. 설정의 활성화 기준과 revert 발생 시 처리 방식은 추가로 확정합니다. 프로젝트·기능 전체의 완료 집계 규칙은 개별 태스크의 완료 규칙과 별도로 정의합니다.

## 기술적 판단과 요약

- PR·이슈 상태, 담당자, 리뷰, CI 결과는 원본 사실로 보존합니다.
- 변경 목적, 영향 범위, 지연 가능성 등의 해석은 근거 링크와 함께 제공합니다.
- 요약에는 대상 범위, 원본 갱신 시각, 생성 시각을 포함합니다. 정보 부족은 미확인으로 표시합니다.
- 구현 완료, 검토 완료, 배포 완료를 구분합니다. 배포 근거가 없으면 출시를 단정하지 않습니다.
- 파일 diff는 PR 본문과 연결 이슈의 맥락 안에서 해석합니다.
- 커밋 수나 변경 줄 수를 개인 생산성 점수로 사용하지 않습니다.

## 공통 서비스와 인터페이스

웹과 MCP는 동일한 애플리케이션 서비스에 연결합니다. GitHub 수집·동기화와 요약 생성은 요청 처리에서 분리한 작업으로 설계합니다. 구체적인 MCP SDK와 전송 방식은 구현 시 공식 사양을 확인하여 정합니다.

```text
웹 UI → 웹 API 어댑터 ─┐
                      ├→ 인증·권한 검사 → 공통 애플리케이션 서비스 → PostgreSQL
MCP 클라이언트 → MCP 어댑터 ┘                       ↑
                                      GitHub 수집·요약 작업
```

공통 기능의 초기 후보는 프로젝트 현황 조회, 기능·목표 등록, 연결 후보 조회·승인·거절, 태스크 검색·생성·수정, PR 변경 조회입니다. 예시 이름은 `get_project_status`, `list_tasks`, `create_task`, `update_task`, `get_pull_request_changes`이며 최종 MCP 계약은 아닙니다. 웹과 MCP 모두 같은 연결 검토 규칙을 적용합니다.

입력·출력 스키마, 필터, 페이지네이션, 오류 형식을 명시합니다. 두 진입점 모두 같은 사용자·조직·저장소 권한을 적용하고, 요약에도 원본 데이터의 접근 제한을 유지합니다. 변경 이력을 기록하고 재시도에 따른 중복 생성 및 동시 수정 충돌을 처리합니다.

## 데이터 소유권 제안

GitHub는 PR·이슈·리뷰·커밋·파일 변경의 원본으로 유지합니다. 내부 시스템은 프로젝트 구성, 태스크, 연결 관계 및 요약을 관리하는 방향을 제안합니다. 태스크 수정이 GitHub 이슈 수정으로 이어지는 양방향 동기화는 정책 확정 전까지 도입하지 않습니다.

## 다음에 정할 사항

1. 프로젝트별 저장소 선택 방식과 AI 연결 후보 탐색 범위.
2. 내부 태스크를 별도로 둘지, GitHub Issues 또는 Projects를 직접 관리할지.
3. YAML 설정의 기준 브랜치·활성화 시점, 완료 후 조건 변경 및 revert 처리, 기능 전체의 완료 집계와 차단 관계.
4. PM 요약의 주기와 갱신 방식, 사람이 판단을 수정하는 방식.
5. 조직 설치 및 사용자 인증 방식, MCP 클라이언트의 사용자 권한 연결.

## Claude 채팅 연결 가능성

2026-10-19 공식 문서 확인 결과, Claude 채팅은 사용자 정의 커넥터를 통해 원격 MCP 서버에 연결할 수 있습니다. cloud-pm-agent는 원격 MCP 엔드포인트를 제공하여 프로젝트 현황 조회와 태스크 관리를 채팅에서 호출할 수 있도록 설계합니다. 실제 연결 검증은 서버 구현 이후 수행합니다.

연결은 Anthropic 클라우드에서 발생하므로 서버는 해당 인프라에서 접근 가능해야 합니다. 로컬 서버만 실행하는 구성으로 claude.ai 연결을 완료할 수는 없습니다. 사용자별 인증을 통해 기존 조직·저장소 권한을 적용하는 방향으로 설계합니다.

사용자는 Claude의 `Customize > Connectors`에서 사용자 정의 커넥터 URL을 등록하고 대화에서 활성화합니다. Team·Enterprise에서는 조직 관리자 측 등록 절차도 필요합니다. 상세 메뉴와 지원 범위는 서비스 변경에 따라 다시 확인합니다.

초기 연결은 상태·태스크·PR 조회 및 태스크 변경 도구를 대상으로 합니다. 채팅 안에 대시보드를 표시하는 인터랙티브 UI는 별도 확장 범위이며, 웹 UI가 그대로 삽입된다고 가정하지 않습니다.

출처: [Claude 공식 원격 MCP 커넥터 안내](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp).

## 구현 현황 (2026-10-20)

웹 대시보드·태스크 관리·파일 diff, 로컬/원격 MCP, PostgreSQL/PGlite 저장, 감사 이력·수정 충돌 검사, 조직 저장소 수집과 YAML 완료 반영을 구현했습니다. Claude API 기술 분석과 연결 제안은 제공자 설정으로 활성화합니다. 기본 브리핑과 키워드 후보는 AI 분석과 구분합니다.

초기 구현은 단일 조직의 공유 워크스페이스입니다. 웹훅 수신·DB 작업 큐·저장소 단위 증분 수집을 추가했습니다. 개별 사용자 OAuth·저장소별 권한·멀티테넌트와 항목 단위 증분 수집은 후속 작업입니다. 앞선 사용자별 인증 설계는 목표이며 현재 구현 완료 범위에 포함하지 않습니다. 태스크는 내부 원본으로 관리하고 GitHub에 역으로 쓰지 않습니다.

## 사용자 및 읽기 화면 추가

프로젝트 생성은 연결 저장소의 검색·선택 방식으로 제공하고, PR·이슈 본문은 안전하게 정제한 GitHub Flavored Markdown으로 표시합니다. 변경 이력은 원문 JSON 대신 작업자·대상·변경 전후 타임라인으로 제공합니다.

사용자는 GitHub 없이 서비스 아이디·비밀번호로 가입하고 워크스페이스 초대로 참여할 수 있습니다. 관리자는 조직용 GitHub 연결을 워크스페이스에 공유할 수 있습니다. GitHub 토큰은 프로필별로 암호화하여 저장하며 원격 MCP용 개인 서비스 토큰을 별도로 발급합니다. 저장소 접근 범위는 개인 또는 관리자 공유 연결로 확인하고, 접근할 수 없는 저장소가 포함된 프로젝트와 관련 태스크·이력은 숨깁니다. 사용자 OAuth·SSO·관리자 사용자 관리와 다중 인증은 구현 범위에 포함되지 않습니다.

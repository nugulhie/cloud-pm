# 변경 이력 조회 메모리 부족 수정 — 2026-11-04

## 원인

운영 DB 로그에서 2026-11-04 06:22:50 UTC에 변경 이력 조회를 실행하던 PostgreSQL 프로세스가 signal 9로 종료된 것을 확인했다. DB 컨테이너의 메모리 제한은 192MB이며 cgroup에 OOM 강제 종료 1회가 기록되어 있었다. 복구 중에는 API가 일시적으로 일반 오류 문구를 반환할 수 있다.

기존 쿼리는 전체 이벤트의 GitHub 파일 patch JSON까지 `lag()`와 정렬에 포함한 뒤 마지막에 300개로 제한했다. 현재 CPU 사용률이 낮아도 이 쿼리의 순간적인 메모리 사용량은 제한을 넘을 수 있었다.

## 변경

- 표시 가능한 종류의 최신 이벤트 ID 300개를 먼저 고른다.
- `(workspace_id, kind, entity_id, revision, created_at, id)` 인덱스로 각 이벤트의 직전 버전을 찾는다. 조회 범위 밖의 이전 버전도 비교한다.
- GitHub 변경 이력 응답에는 대형 파일 patch 대신 파일 수와 PR 커밋 식별자를 포함한다. GitHub 활동의 diff와 저장된 원본 이벤트는 유지한다.
- 기존 Markdown 본문, 권한 필터, 워크스페이스 격리, 최종 표시 개수 100개 제한은 유지한다.

기존 운영 DB에는 `maintenance_work_mem=8MB`로 인덱스를 먼저 생성하고 앱을 교체한다. 자동 초기화 스키마에도 같은 인덱스를 포함한다. 데이터를 삭제하거나 컨테이너 메모리 제한을 늘리지 않는다.

## 검증

- 기존 관리·완료 처리·사용자·워크스페이스 검사 13개 통과.
- 최신 범위 밖의 이전 버전, Markdown 원문, 대형 diff 제외, 워크스페이스 격리를 다루는 회귀 검사 3개 통과.
- PostgreSQL 18 컨테이너를 운영과 같은 192MB로 제한하고 이벤트 22,000개, 합계 458,752,000자의 합성 patch를 넣어 실행했다. 새 쿼리는 300개를 약 65ms에 조회했고 이전 버전 인덱스를 사용했다. OOM 종료는 없었다. 합성 데이터 결과이며 운영 응답 시간을 보장하는 수치는 아니다.
- 타입 검사 통과. 검증 로그와 실행 계획은 무시되는 `.data/design-update-20261104/`에 보관한다.

운영 검증은 과거의 OOM 플래그를 지우기 위한 재시작 대신 cgroup의 `oom_kill` 횟수가 더 증가하는지 확인한다. 기존의 전체 이력 쿼리를 운영에서 재현하지 않는다.

## 운영 적용 결과

`history-memory-20261104` 릴리스로 앱과 워커를 교체했다. 운영 데이터의 새 쿼리는 300개 후보를 약 4.23초에 조회했고 이전 버전 인덱스를 사용했다. 검증 직후 DB의 `oom_kill`은 적용 전과 같은 1회였으며, 앱과 워커는 정상 상태였다. 이는 한 번의 운영 조회 확인이며 지속 부하 검증을 뜻하지 않는다.

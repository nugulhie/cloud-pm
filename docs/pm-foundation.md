# PM 기본 기능 구성

현재 UI는 기능과 태스크를 하나의 작업으로 관리한다. 초기 설계의 기능 묶음 설명은 [현재 작업 모델](work-items.md)을 기준으로 읽는다. 최신 구현 점검과 미구현 기능의 우선순위는 [UX·기능 점검](ux-product-audit.md)을 참고한다.

## 제품 방향

Asana처럼 PM이 쉽게 작업을 정리하고 여러 뷰에서 확인할 수 있게 하고, Jira의 개발 작업 추적 방식과 GitHub 근거를 결합한다. 범용 PM 기본 기능 위에 조직 전체의 PR·이슈 집계, 파일 변경 확인, 기술적 요약, YAML 완료 판정, MCP 인터페이스를 제공한다.

참고: [Asana 프로젝트 관리](https://asana.com/features/project-management), [Jira 기능](https://www.atlassian.com/software/jira/features). 아래 항목은 이 저장소의 구현 상태이며 두 제품의 요금제별 제공 범위를 뜻하지 않는다.

## 현재 제공

| 영역                 | 구현 범위                                                                           |
| -------------------- | ----------------------------------------------------------------------------------- |
| 프로젝트·기능·태스크 | 이름·목표·담당자·우선순위·기한·차단 사유, 개별/일괄 추가·수정·삭제                  |
| 작업 보기            | 같은 태스크의 목록·보드 보기와 상태 변경, 보드 드래그 앤 드롭                       |
| 일정                 | 프로젝트 시작·종료일과 월간 캘린더. 태스크 기간 타임라인은 미구현                   |
| GitHub               | PR·이슈 선택 가져오기, 프로젝트·기능 연결 표시, 파일 diff·작성자 확인               |
| 협업 진입            | 개인 프로필·토큰, 같은 조직 멤버 초대, 초대 전용 가입 설정                          |
| 댓글·알림            | Markdown 댓글·본인 수정/삭제, 구성원 멘션, 담당자·대화 참여자 알림과 개인 읽음 상태 |
| 변경 근거            | 변경 이력과 Markdown 본문, YAML PR 머지 조건에 따른 태스크 완료                     |

기능은 브랜치와 별개로 태스크를 묶는 관리 단위이다. 사용자 기능만 담을지 기술 개선·운영을 포함한 작업 묶음으로 넓힐지는 용어와 집계 정책을 함께 정한다. 기존 YAML 식별자를 임의로 변경하지 않는다.

## 추가 구현 순서 제안

1. **작업 구조**: 태스크 종류(기능 개발·버그·개선·운영), 라벨, 하위 작업, 섹션·기능별 그룹핑, 내 작업 화면.
2. **협업 확장**: 댓글·멘션·앱 내 알림은 구현했다. 수동 구독 설정, 이메일·Slack 알림과 담당자 변경 알림을 후속으로 추가한다.
3. **일정 확장**: 선행·후행 의존성과 순환 검증은 구현했다. 태스크 시작일·종료일, 마일스톤, 타임라인과 일정 충돌 검증을 후속으로 추가한다.
4. **팀 운영**: 워크스페이스 관리자·편집자·조회자 역할, 프로젝트별 참여자. 외부 게스트는 저장소 정보 공개 범위를 별도로 설계한다.
5. **확장**: 사용자 정의 필드·워크플로, 템플릿, 규칙 자동화, 저장한 보기, 스프린트·백로그, 작업량·프로젝트 포트폴리오.

각 항목은 아직 구현되지 않은 후속 범위이다. 공유 데이터·권한·감사 이력을 웹과 MCP에서 동일하게 적용한다. 태스크는 직접 완료·재개방할 수 있으며 PR 조건에 따른 자동 완료도 제공한다.

## 기능 정의와 하위 태스크

기능은 Git 브랜치와 독립된 제품 작업 묶음이다. 목표(`goal`)와 Markdown 인수 기준(`acceptanceCriteria`)을 등록하고 태스크를 연결한다. 인수 기준은 검토를 위한 설명이며 자동 완료 조건을 대체하지 않는다.

태스크의 `type`은 `feature`(기능 개발), `bug`(버그), `improvement`(개선), `operations`(운영)이다. 기존 태스크는 기능 개발로 표시한다. `parentId`로 같은 워크스페이스·프로젝트·기능의 작업을 연결하며, `null`이면 최상위 작업이다. 순환 연결은 허용하지 않는다. 상위 작업을 삭제하면 모든 하위 작업과 GitHub 연결도 삭제한다. 각 태스크는 직접 완료하거나 YAML PR 머지 조건으로 자동 완료한다. 하위 작업의 완료가 상위 작업을 자동 완료시키지는 않는다. 보드의 계층 보기와 상세 하위 목록에서 펼치기·추가·완료 개수를 확인한다.

웹 태스크 관리 화면과 MCP `create_task`/`update_task`에서 같은 필드를 사용한다. MCP `list_tasks`는 `type`, `parentId` 필터를 지원하며 `parentId: null`로 최상위 작업만 조회할 수 있다. 기능 인수 기준은 기능 추가·수정 화면과 MCP `create_feature`/`update_feature`에서 관리한다.

## 댓글·멘션·앱 내 알림

태스크 상세의 댓글에서 Markdown 작성과 본인 댓글 수정·삭제를 지원한다. 개인 사용자 인증과 쓰기 권한이 필요하며, 읽기 권한의 사용자는 댓글을 조회할 수 있다. GitHub 원본의 댓글과는 별도이며 GitHub에 전송하지 않는다.

`@GitHub아이디`로 해당 프로젝트의 저장소에 접근 가능한 워크스페이스 구성원을 멘션한다. 멘션 대상·담당자·기존 댓글 작성자에게 앱 내 알림을 제공하고 본인은 제외한다. 코드 블록과 인라인 코드의 멘션은 알리지 않는다. 현재 GitHub 저장소 권한과 워크스페이스 범위를 적용하므로 접근할 수 없어진 작업의 댓글·알림은 노출하지 않는다.

상단 알림함과 열린 댓글은 30초마다 갱신하며 수동 새로고침도 지원한다. 알림에서 태스크로 이동하거나 모두 읽음으로 처리할 수 있다. 읽음 상태는 사용자·워크스페이스별로 저장되며, 댓글 수정은 새 버전으로 미읽음 처리된다. 댓글이나 태스크를 삭제하면 관련 알림은 더 이상 표시하지 않는다. 이메일·Slack 알림, 담당자 변경 자체의 알림, 푸시 알림은 제공하지 않는다.

MCP 도구: `list_task_comments`, `add_task_comment`, `update_task_comment`, `delete_task_comment`, `list_notifications`, `mark_notification_read`. 작성·수정·삭제 및 알림은 개인 MCP 토큰을 사용한다. 수정·삭제·읽음에는 조회 결과의 `revision`을 전달한다. 공용 레거시 토큰으로 개인 댓글을 작성할 수 없다.

## 태스크 선행·후행 의존성

`dependsOn`에 선행 태스크 식별자를 등록한다. 같은 워크스페이스·프로젝트 안에서 기능을 가로질러 최대 100개를 선택할 수 있다. 상위·하위 관계와는 별개의 계획 관계이며 자기 참조와 순환 연결은 허용하지 않는다. 필드를 생략한 기존 클라이언트의 수정은 관계를 보존하며 빈 배열로 해제한다.

선행 작업이 모두 `done`일 때 대기 표시를 해제한다. 취소한 선행 작업은 관계를 명시적으로 해제한다. 보드·목록·개입 필요 항목에 미완료 선행 작업을 표시하며 **선행 대기만** 필터로 모아 본다. 검색이나 담당자 필터로 가려진 선행 작업도 전체 프로젝트 데이터로 평가한다. 상태와 완료는 사용자가 직접 변경할 수 있고 YAML PR 머지 조건의 자동 완료도 지원한다. 완료·취소된 후행 태스크는 대기 필터에서 제외한다.

후행 작업이 남아 있으면 선행 태스크 삭제를 차단한다. 관계를 해제하거나 관련 작업을 함께 삭제한다. 프로젝트·기능·상위 태스크의 연쇄 삭제에도 같은 보호를 적용한다. 관계 수정·삭제는 트랜잭션과 프로젝트 행 잠금으로 동시 요청의 순환 연결과 끊어진 참조를 방지한다.

MCP `create_task`/`update_task`에서 `dependsOn`을 설정하고 `get_task_dependencies`에서 선행·후행 목록과 차단 여부를 조회한다. `list_tasks`는 `blocked`, `dependsOn` 필터를 제공한다. 웹 API는 `GET /api/tasks/dependencies?task=<id>`이다.

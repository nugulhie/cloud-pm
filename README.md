# cloud-pm-agent

GitHub 조직의 PR·이슈·파일 변경을 모아 PM의 현황 파악과 개발자의 태스크 관리를 지원합니다. Next.js·TypeScript 기반 웹과 MCP가 같은 애플리케이션 서비스를 사용합니다.

## 프로젝트와 태스크 확인

- **프로젝트 현황** 상단에서 프로젝트별 완료율·일정·담당자·차단 수를 확인합니다. 취소한 태스크는 완료율에서 제외하며, 검색·담당자·상태 필터를 적용하면 해당 범위를 집계합니다. 개별 태스크는 6개를 미리 보여 주고 전체 작업은 태스크 보드로 연결합니다.
- **PRD 관리**는 번호·기능명·상태·담당자·태스크 연결을 보여 주는 **간단 보기**가 기본입니다. **전체 열 보기**에서 설명·정책·비고·편집 정보를 함께 확인합니다.
- 태스크 제목을 누르면 본문·상태·GitHub 연결·하위 작업을 읽는 상세 패널이 열립니다. 상태는 상세에서 바로 바꾸고, 나머지 내용은 **태스크 수정**에서 편집합니다.
- 모바일에서는 상단 **메뉴 열기**로 업무·문서·활동·관리 메뉴에 접근합니다. 외부 프로젝트 가져오기와 현황의 수동 동기화는 **더 보기**에 있습니다.

[디자인 점검과 개선 내역](docs/design-review-2026-11-04.md)을 참고하세요.

## PRD 작성과 개발 작업 연결

왼쪽 **PRD 관리**에서 프로젝트별 요구사항을 작성합니다. 표는 넘버링, 기능명, 상세설명, 정책, 비고, 상태, 최종 편집일시, 편집자, 담당자를 제공합니다. 상세설명·정책·비고는 Markdown을 지원합니다. `PRD-001` 형식의 번호와 편집 정보는 서버에서 자동 기록합니다. CSV의 원본 ID가 있으면 `TCO-1` 같은 ID를 넘버링으로 표시하고 내부 번호도 유지합니다.

- **CSV 가져오기**에서 프로젝트와 UTF-8 CSV를 선택하고 **파일 미리보기 → PRD에 가져오기**를 누릅니다. Notion의 `ID·기능명·상세 설명·정책·비고·최종 편집 일시·최종 편집자` 형식을 지원하며, 열 순서는 상관없습니다. 상태·담당자 열도 선택적으로 가져옵니다. 원본 편집 정보와 시스템 편집 정보는 구분해 보존합니다.
- 같은 프로젝트의 ID가 겹치면 기본적으로 건너뜁니다. **CSV에 있는 열로 기존 PRD 수정**을 선택하면 파일에 있는 열만 수정하며, 연결된 태스크·이슈와 파일에 없는 상태·담당자·정책 참조는 유지합니다. 파일 오류나 동시 변경이 있으면 전체 가져오기를 취소합니다. 최대 1 MiB·500행이며 [CSV API 명세](docs/prd-import.openapi.yaml)를 제공합니다.
- 항목을 선택하고 **선택 항목 → 태스크**를 누르면 상세설명·정책·비고·담당자를 복사합니다. 기능을 따로 선택하지 않고 각 PRD를 하나의 작업으로 만듭니다. 한 번에 최대 100개를 전환하며, 이미 전환된 항목은 중복 생성하지 않습니다.
- **GitHub 이슈 생성**은 미전환 PRD에서도 열 수 있습니다. **태스크로 전환하고 계속 → 대상 저장소 선택 → 본문 미리보기 → GitHub에 이슈 생성** 순서로 진행하며 이미 태스크가 있으면 전환 단계를 생략합니다. 저장소가 없으면 이유와 **프로젝트 저장소 설정** 경로를 표시합니다. 발행한 이슈는 태스크에 연결되고 PRD 표에서 열 수 있습니다. GitHub App 또는 개인·워크스페이스 공용 GitHub 연결의 대상 저장소 **Issues 쓰기 권한**이 필요합니다. [GitHub 이슈 생성 API](https://docs.github.com/en/rest/issues/issues#create-an-issue)를 사용합니다.
- PRD 상태는 기획자가 직접 관리합니다. 태스크는 직접 완료하거나 YAML 머지 조건으로 자동 완료할 수 있으며, PRD 수정은 이미 생성된 태스크·GitHub 이슈를 자동 덮어쓰지 않습니다. 담당자는 GitHub 사용자 목록에서 선택하며 이슈 발행 시 GitHub의 Assignees에도 반영합니다.
- 동시 편집은 `revision`으로 충돌을 알립니다. 이슈 생성 응답이 불명확하면 중복 생성을 막고 원본 확인이 필요하다고 표시합니다. 데모에서는 미리보기까지 제공하고 실제 외부 발행은 차단합니다.
- 연결된 태스크·이슈 이력이 없는 PRD만 삭제할 수 있습니다. 연결된 항목은 보류 상태로 관리합니다. 프로젝트 삭제는 내부 PRD·기능·태스크를 함께 제거하며 GitHub 원본은 유지합니다.

MCP에서도 `list_requirements`, `save_requirement`, `convert_requirements_to_tasks`, `preview_requirement_issue`, `publish_requirement_issue`, `delete_requirements`를 제공합니다. 쓰기 도구는 쓰기 권한이 있는 연결에만 노출됩니다.

프로젝트 생성·수정에서 5자리 기능 식별자를 지정하거나 자동 생성하면 PRD 번호를 `ADMIN-001` 형식으로 통일합니다. GitHub 담당자 선택·저장소별 배정 검사·기존 CSV 원본 ID 보존 규칙은 [PRD 담당자와 프로젝트 번호](docs/prd-github-assignees.md)를 참고하세요.

## 정책 저장소와 용어집

왼쪽 **정책 저장소**에서 정책명·내용·분류·담당자·비고·상태를, **용어집**에서 용어명·정의·별칭·약어를 작성합니다. Markdown, 검색, 상태·분류 필터, 수정 충돌 확인, 삭제, 자동 편집 이력을 제공합니다. 문서는 현재 워크스페이스에 공유되며 조회 전용 멤버는 편집할 수 없습니다.

각 카드의 **연결·영향 보기**에서 관련 PRD·태스크·하위 작업·이슈·PR을 모아 보고 프로젝트별로 필터링할 수 있습니다. 편집 화면에서도 저장 전에 영향 범위를 확인합니다. PRD·태스크 제목을 누르면 상세로 이동하며 GitHub 원문은 새 창으로 열립니다. 목록은 40개씩 표시하고 마지막 수정·활동 시각과 연결 근거를 제공합니다. PRD의 **정책 선택·용어 선택**에서 검색 후 체크하고, 선택 버튼의 **×**로 바로 해제합니다. 검색하거나 목록을 접어도 선택은 유지됩니다. 정책 편집의 **따르는 정책**에서 기준 정책을 등록하면, 기준 정책의 영향 조회에 의존 정책을 사용하는 PRD와 작업도 포함됩니다. **직접 참조만** 필터와 **의존 정책** 탭에서 범위와 경로를 확인합니다. 자기 참조·순환 의존은 차단하고 참조 중인 정책은 삭제를 보호합니다. PRD 작성 시 관련 정책·용어를 각각 최대 10개 선택할 수 있습니다. 참조 중인 문서는 삭제 대신 **사용 중단** 상태로 관리합니다. GitHub 이슈 생성 시 현재 참조 문서의 내용을 문서당 2000자까지 발췌해 포함하며, 이슈 생성 후 문서 변경은 원본 이슈를 자동 수정하지 않습니다. MCP에서는 `list_knowledge`, `get_knowledge_impact`, `save_knowledge`, `delete_knowledge`를 제공합니다. [영향 조회 계약](docs/knowledge-impact.md)에서 집계·권한·페이지 규칙을 확인하세요.

## 바로 실행

Node.js 24 이상과 npm이 필요합니다.

```sh
npm ci
npm run demo
```

브라우저에서 <http://127.0.0.1:3000>을 엽니다. 데모는 예시 프로젝트·작업자·PR을 별도 로컬 DB에 저장하며 실제 GitHub나 AI API를 호출하지 않습니다. 개발 모드에서만 활성화할 수 있습니다.

## 통합 작업과 GitHub 필터

기능과 태스크는 같은 작업입니다. **기능·태스크 추가**에서 프로젝트와 제목을 입력하면 등록되며, 별도의 기능 등록·선택이 필요 없습니다. 항목 관리의 일괄 추가와 GitHub 선택 가져오기도 프로젝트만 선택합니다. 기존 기능 중 작업이 없던 항목은 첫 쓰기 사용자 접속 시 작업으로 이관하며, 기존 작업·PRD·YAML 연결은 보존합니다. [호환 API와 이관 규칙](docs/work-items.md)을 참고하세요.

GitHub 활동의 **전체 / PR만 보기 / 이슈만 보기**는 기존 상태·검색·닫힌 항목 숨김과 함께 적용됩니다. 프로젝트를 선택하면 연결 저장소의 PR·이슈만 표시하고 **GitHub 동기화**도 해당 저장소로 제한합니다. 목록과 상세에서 라벨·담당자·개인 및 팀 리뷰 요청 대상을 확인합니다. 예전 캐시의 라벨은 다음 동기화에서 채워집니다. GitHub 필드는 [이슈 API](https://docs.github.com/en/rest/issues/issues)와 [리뷰 요청 API](https://docs.github.com/en/rest/pulls/review-requests)를 기준으로 수집합니다.

## Asana 프로젝트 가져오기

**프로젝트 현황 → 외부 프로젝트 가져오기**에서 Asana CSV·JSON 파일을 선택하면 프로젝트와 선택한 작업·하위 작업을 함께 생성합니다. 파일당 최대 **10,000개 작업·10MiB**를 지원하며 미리보기는 50개씩 표시합니다. 기존 프로젝트나 GitHub 연결 없이 시작하고, 프로젝트 이름·목표·일정을 미리 확인할 수 있습니다. 같은 원본 프로젝트를 다시 가져오면 기존 프로젝트를 사용하며 기존 유지 또는 갱신을 선택합니다. 작업 없는 프로젝트도 지원합니다. [형식과 API·MCP 안내](docs/asana-import.md)를 참고하세요.

## 제공 기능

- PM 대시보드: 통합 기능·태스크의 완료 상태, 진행 작업, 담당자 미지정·차단·기한 초과·연결 PR의 CI 실패·리뷰 요청.
- 프로젝트 생성: 연결 저장소 검색·다중 선택, 목표·식별자 등록.
- 읽기 화면: PR·이슈 본문의 GFM Markdown 미리보기·원문 전환, 작업자·변경 전후를 표시하는 이력 타임라인.
- 태스크 보드: 프로젝트 아래 기능·태스크 바로 등록, 담당자·상태·우선순위·기한·차단 사유 관리, 필터와 검색.
- GitHub: 접근 가능한 조직 저장소의 이슈·PR, 작성자·담당자·리뷰 요청자·커밋 작성자, 파일별 변경과 diff 수집.
- 연결 관리: 직접 연결, 키워드 또는 AI 후보 제안, 사람의 승인·거절. 기존 결정을 재분석으로 덮어쓰지 않습니다.
- 완료 처리: PR 없이 상태를 완료로 바꾸고 필요하면 재개방합니다. 기본 브랜치의 `.cloud-pm/tasks/*.yaml`에 정의한 PR·대상 브랜치와 `all`·`any` 조건에 따른 자동 완료도 지원합니다.
- 요약: 규칙 기반 브리핑 및 선택적 Claude API 기술 분석. AI 분석은 사실·해석·미확인 항목과 원본 식별자를 구분합니다.
- 저장: PostgreSQL 또는 로컬 PGlite, 수정 충돌 감지, 감사 이력, 동기화 결과.
- 태스크 의존성: 같은 프로젝트의 선행·후행 작업, 선행 대기 표시·필터, 순환 연결·참조 중 삭제 보호를 웹과 MCP에서 제공합니다.
- 댓글·알림: 태스크 Markdown 댓글·본인 수정/삭제, 구성원 멘션, 담당자·대화 참여자의 개인 알림함과 읽음 처리. 웹·MCP에서 지원하며 GitHub 원본 댓글과 별도로 관리합니다.
- MCP: 원격 Streamable HTTP와 로컬 stdio에서 조회·태스크 관리·연결 승인·동기화·AI 분석 제공.

완료 태스크 비율은 등록된 업무 범위의 집계이며 프로젝트 출시율을 의미하지 않습니다. QA·배포는 PR 머지와 구분합니다.

## 항목 관리와 일정

- **항목 관리**에서 프로젝트·기능·태스크를 선택해 수정·삭제합니다. 일괄 추가는 한 줄에 이름 하나씩 입력하고, 선택 수정은 공통 필드에 적용합니다. 최대 100개씩 처리하며 일부 수정 실패 시 결과를 표시합니다.
- **프로젝트 현황 → 프로젝트 목록 → 삭제**로 프로젝트를 바로 삭제합니다. 프로젝트를 선택한 경우 상단의 **프로젝트 삭제**도 사용할 수 있습니다. 확인창에서 함께 삭제될 작업·PRD·연결 개수를 확인한 뒤 확정합니다. 프로젝트 수정·일괄 삭제는 **프로젝트 관리**에서 진행합니다.
- **태스크 보드**에서 카드를 완료 열로 드래그하거나 상태 메뉴에서 완료를 선택합니다. 완료 작업도 다른 상태로 재개방할 수 있습니다. **항목 관리 → 선택 항목 일괄 수정 → 상태**에서 최대 100개를 함께 변경합니다. PR 자동 완료 조건이 계속 충족된 작업은 재개방 후 다음 동기화에서 다시 완료될 수 있습니다.
- **계층 보기**에서 부모를 펼쳐 하위 태스크를 확인하고 **＋ 하위**로 바로 추가합니다. 상세 창에서도 하위 목록·완료 개수·추가·상위 이동을 제공합니다. 하위 태스크는 담당자·기한·상태를 독립적으로 관리하며 여러 단계로 나눌 수 있습니다. Asana의 명확한 상하위 관계도 같은 화면에 표시합니다.
- 태스크 보드는 **계층 보기가 기본**이며 제목·상태·담당자·기한을 같은 위치에 표시합니다. 프로젝트 선택과 검색은 상단에 두고 담당자·상태·유형·선행 대기는 **필터**에서 설정합니다. 전체 프로젝트 범위에는 프로젝트명을, 기한 초과·차단 작업에는 사유를 표시합니다. 보드의 가로 이동은 보드 영역 안에서만 발생합니다.
- 태스크 상세는 기본 정보 → 하위 태스크 → 추가 설정 순서입니다. 고급 설정과 GitHub 연결은 기본적으로 접혀 있습니다. 작성 중 다른 태스크로 이동·추가하려 하면 현재 입력을 유지하고 먼저 저장하도록 안내합니다. [UX·디자인 점검](docs/task-ux-review.md)을 참고하세요.
- **GitHub 활동**은 닫힌 PR·이슈와 머지 완료를 기본적으로 숨깁니다. **닫힌 PR·이슈 숨기기**를 해제하거나 상태 필터에서 닫힘·머지 완료를 선택하면 다시 볼 수 있습니다. 원본 데이터는 삭제하지 않습니다.
- **GitHub 활동**은 승인된 연결의 프로젝트·기능을 항목 옆에 표시합니다. 여러 연결은 모두 표시하고 같은 프로젝트·기능은 중복 표시하지 않습니다. PR·이슈를 개별 또는 검색 결과 전체 선택한 뒤 프로젝트·기능을 지정해 태스크로 가져옵니다. 같은 기능에 이미 연결된 항목은 건너뜁니다. 머지된 PR도 저장소 YAML의 완료 조건 평가를 거쳐 완료됩니다.
- 프로젝트 생성·수정 시 `startDate`, `endDate`를 `YYYY-MM-DD`로 지정합니다. **캘린더**는 월별 프로젝트 기간과 시작·종료일을 표시합니다. 한쪽 날짜만 지정하면 해당 날짜에 표시합니다.
- 삭제는 관리 항목과 하위 태스크·연결에 적용하며 감사 이력을 보존합니다. GitHub 원본은 삭제하지 않습니다. 삭제된 식별자는 재사용하지 않으므로 새 항목에는 새 식별자를 사용하세요.
- 변경 이력은 최초 등록값과 수정 전후를 구분하고, 본문·목표·설명은 접기·펼치기 Markdown으로 표시합니다.

## 실제 GitHub 연결

조직 GitHub App으로 PAT 없이 연동하려면 [App 등록·설치와 서버 설정](docs/github-app-setup.md)을 따릅니다. App 설치 범위는 지정한 워크스페이스에 공유하며 서버에서 설치 토큰을 자동 갱신합니다. 아래는 기존 PAT 연결 방법입니다.

```sh
cp .env.example .env
npm run dev
```

`.env`에 `GITHUB_ORG`, `GITHUB_TOKEN`, `APP_READ_TOKEN`, `APP_WRITE_TOKEN`을 설정하고 화면의 연결 설정에 서비스 접근 토큰을 입력합니다. GitHub 토큰을 화면에 입력하지 않습니다. 서버 토큰은 대상 저장소의 Metadata·Contents·Issues·Pull requests 읽기 권한이 필요하며, CI 조회에는 Checks·Commit statuses 읽기 권한도 필요합니다. 조직 정책에 따라 토큰 승인·SSO 설정이 필요할 수 있습니다.

먼저 프로젝트·기능·태스크를 등록하고 개발자가 [YAML 예제](examples/tasks/social-login.yaml)를 실제 식별자로 수정해 저장소 기본 브랜치에 반영합니다. 화면의 “GitHub 동기화” 또는 다음 명령으로 수집과 완료 판정을 실행합니다.

```sh
npm run sync
npm run evaluate -- my-org/config-repository
```

`sync`는 DB에 동기화하고, `evaluate`는 저장소 하나를 JSON으로 평가하는 조회 전용 CLI입니다. 후자는 환경 변수를 직접 전달하거나 `node --env-file=.env --import tsx src/cli.ts owner/repo`로 실행합니다. 최초 수집 이후에는 웹훅 작업자로 변경 항목만 반영하며 정기 전체 수집 cron은 등록하지 않습니다. 수동 동기화는 누락 복구에 사용합니다. 기본 브랜치 SHA를 고정하여 설정 파일 간 일관성을 유지하며 잘못된 설정·중복 태스크·조회 실패는 오류 또는 미확인으로 남깁니다.

이력이 많은 조직은 `GITHUB_SYNC_SINCE`에 ISO 8601 시각을 지정할 수 있습니다. 열린 작업은 모두 수집하고, 닫힌 PR·이슈는 해당 시각 이후 변경된 항목부터 수집합니다. 기준일은 수집의 시작 시각이며 종료일을 제한하지 않습니다. 화면은 GitHub 원본 변경 시각의 최신순으로 정렬하며 원본 변경 시각과 마지막 데이터 수집 시각을 따로 표시합니다. 미설정 시 전체 이력을 수집합니다. [GitHub Issues API](https://docs.github.com/en/rest/issues/issues)의 갱신 시각 필터를 사용합니다. 화면의 15초 갱신은 저장된 데이터의 재조회이며 원본 자동 수집이 아닙니다. 최초 수집과 누락 복구는 수동 동기화로, 이후 변경은 연결된 웹훅 작업자로 반영합니다.

## GitHub 웹훅 자동 동기화

`.env`에 `GITHUB_WEBHOOK_SECRET`을 설정하고 GitHub 조직 웹훅의 Payload URL을 `https://서비스주소/api/webhooks/github`, Content type을 `application/json`, Secret을 동일한 값으로 등록합니다. 서명 검증 후 DB 큐에 저장하고 즉시 응답합니다. 중복 delivery는 다시 실행하지 않습니다.

웹과 작업자가 동일한 PostgreSQL을 사용하도록 `DATABASE_URL`을 설정한 뒤 별도 프로세스에서 실행합니다.

```sh
npm run worker           # 대기 중인 작업을 계속 처리
npm run worker -- --once # 작업 하나 처리 후 종료
```

이슈·PR 메타데이터는 웹훅 본문으로 반영하고, 변경된 PR의 diff·CI만 추가 조회합니다. 기본 브랜치 push는 해당 저장소 YAML 색인만 갱신하며 완료 조건은 캐시로 평가합니다. API 한도 초과는 재설정까지 대기하며 일반 실패는 최대 5회 자동 재시도하고, 중단된 작업은 90초 임대 만료 후 복구합니다. 웹의 “작업 큐”와 MCP에서 상태 확인·실패 작업 재시도가 가능합니다. 화면은 편집 중이 아닐 때 15초마다 갱신합니다.

지원 이벤트·운영 방법과 검증 범위는 [웹훅 안내](docs/webhooks.md)를 확인하세요. GitHub 웹훅 등록과 외부 HTTPS 연결은 자동 실행하지 않습니다.

## DB와 운영 실행

`DATABASE_URL`이 없으면 PGlite가 `.data/cloud-pm`에 저장합니다. 로컬 DB는 하나의 프로세스에서 사용하세요. 웹과 독립 MCP·스케줄러를 함께 실행할 때는 PostgreSQL을 사용합니다.

```sh
docker compose up -d db
# .env의 DATABASE_URL을 설정한 다음 실행
npm run build
npm start
```

시작 시 필요한 테이블을 생성하고 기존 데이터는 유지합니다. 운영 전 DB 백업·접근 정책과 HTTPS 프록시를 구성하세요. 현재 서비스는 **하나의 GitHub 조직 안에서 여러 워크스페이스**를 지원합니다. 사용자 등록·비밀번호 로그인·프로필별 암호화된 GitHub 토큰과 개인 MCP 토큰을 제공합니다. 워크스페이스 멤버십과 개인/관리자 공유 저장소 권한을 화면·API·MCP·변경 이력에 적용하며 프로젝트는 연결 저장소 모두에 접근할 수 있을 때만 표시합니다. OAuth·SSO·여러 GitHub 조직 연결은 후속 범위입니다.

## 개인 설정과 GitHub 연결 표시

왼쪽 아래 프로필을 누르면 **프로필 / GitHub 연결 / MCP·API / 워크스페이스 / 보안** 탭으로 설정을 관리합니다. 태스크 계층·목록·보드에는 승인된 이슈·PR 번호가 표시되며 태스크 상세에서 제목·원본 링크·상태를 바로 확인할 수 있습니다. [개인 설정 안내](docs/account-settings.md)를 참고하세요.

## 워크스페이스 생성과 전환

로그인 후 왼쪽 상단의 워크스페이스 버튼에서 이름과 설명을 입력해 새 공간을 만듭니다. 프로젝트·기능·태스크·멤버·초대가 분리되며 기존 데이터는 기본 워크스페이스에 보존됩니다. 현재 하나의 GitHub 조직 안에서 여러 워크스페이스를 지원합니다. [워크스페이스 안내](docs/workspaces.md)를 확인하세요.

개인 MCP 토큰은 발급 당시 워크스페이스에 고정됩니다. 웹 전환으로 Claude의 작업 대상이 바뀌지 않습니다. 다른 워크스페이스용 토큰을 재발급하면 이전 토큰이 무효화됩니다.

## 사용자·프로필 설정

서버의 `TOKEN_ENCRYPTION_KEY`에 32바이트 무작위 키의 hex 문자열을 설정합니다. 로컬 연결 환경에는 설정되어 있으며 다른 환경에서는 별도로 생성해야 합니다. 이 키와 DB를 안전하게 백업하세요. 키를 임의 변경하면 기존 GitHub 토큰을 복호화할 수 없습니다.

왼쪽 아래 개인 프로필을 눌러 “계정 등록”에서 서비스 아이디(영문·숫자·하이픈 3~39자)와 10자 이상의 비밀번호로 등록합니다. GitHub 계정·토큰 없이 가입할 수 있습니다. 이후 서비스 아이디·비밀번호로 로그인하며, 기존 GitHub 아이디 기반 계정도 그대로 사용할 수 있습니다. 관리자는 “워크스페이스 GitHub 연결”에 조직 연동 토큰을 등록하거나 개인 연결을 공유합니다. 공유 연결의 저장소는 해당 공간의 멤버에게 공개되며, 수정 역할은 PRD 기반 이슈를 생성할 수 있습니다. 같은 창의 “워크스페이스 멤버·초대”에서 멤버 조회와 초대 링크 발급·취소, 초대 전용 가입 설정을 제공합니다. 최초 가입자가 소유자가 됩니다. 프로필에서는 표시 이름·GitHub 토큰·비밀번호를 변경하고, 개인 MCP 토큰을 조회 전용 또는 조회·수정 권한으로 발급·회전·폐기할 수 있습니다. GitHub 토큰 원문을 다시 내려주지 않으며 새 MCP 토큰은 발급 직후에만 표시합니다.

첫 사용자가 등록되면 기존 공용 서비스 토큰은 기본적으로 비활성화됩니다. 현재 세션을 사용자 로그인으로 전환하고 MCP에도 개인 토큰을 설정하세요. `ALLOW_LEGACY_ACCESS=true`는 공용 토큰의 기존 전체 워크스페이스 접근을 다시 허용하는 호환 옵션이므로 운영에서는 사용하지 않습니다.

비밀번호는 scrypt, GitHub 토큰은 AES-256-GCM으로 저장합니다. 로그인 쿠키는 HttpOnly·SameSite=Lax이며 HTTPS에서 Secure를 설정합니다. 저장소 권한은 최대 60초 캐시한 뒤 재검증하고 확인 실패 시 데이터 접근을 거부합니다. 로그인 시도는 계정별 15분당 10회로 제한합니다. 워크스페이스 역할 변경·멤버 제외를 지원하며 비밀번호 분실 복구·계정 전체 삭제·다중 인증은 아직 제공하지 않습니다. 자세한 흐름은 [사용자 안내](docs/users.md)를 참고하세요.

## AI와 MCP

AI 분석은 `ANTHROPIC_API_KEY`와 `ANTHROPIC_MODEL` 설정 후 프로젝트를 선택하여 실행합니다. 선택 프로젝트의 태스크·PR 본문·일부 diff를 제공자에 전송합니다. 응답의 근거 식별자를 검증하며 AI가 상태를 변경하지 않습니다. 모델 판단의 정확성을 자동 보증하지 않으며 검토가 필요합니다.

원격 MCP 주소는 `/api/mcp`입니다. Claude 커넥터에서 접근 가능한 HTTPS 주소와 `Authorization: Bearer <프로필에서 발급한 개인 서비스 토큰>` 헤더를 등록합니다. 개인 토큰은 해당 프로필의 저장소 접근 권한과 조회·수정 권한을 적용합니다. OAuth 자동 로그인은 미구현입니다. 로컬 연결은 다음 명령을 stdio 서버로 등록합니다.

```sh
npm run mcp
```

자세한 도구 목록과 연결 조건은 [MCP 안내](docs/mcp.md)를 확인하세요.

## 개발과 검증

```sh
npm test             # YAML·GitHub·DB·서비스·AI 응답 검증·MCP 테스트
npm run mcp:check    # 환경에 지정한 개인 토큰으로 MCP 인증·도구 조회
npm run typecheck
npm run lint        # Prettier 형식 검사
npm run format
npm run build
npm run test:e2e    # Chrome 기반 화면 조작·모바일·HTTP MCP 검증
```

E2E는 실데이터와 분리된 3100번 포트·로컬 DB·별도 빌드 경로에서 로컬 Google Chrome을 사용합니다. CI 브라우저 실행은 별도 설치가 필요합니다. API 토큰이나 실조직 데이터 없이 수행하는 테스트와 실제 연결 검증을 구분합니다.

구조: `src/app/` 웹·API, `src/core/` 공통 서비스, `src/db/` 저장, `src/github/` 수집, `src/completion/` 완료 평가, `src/mcp/` MCP 도구, `src/ai/` AI 어댑터, `tests/` 자동 테스트.

## 현재 한계

실제 조직·Claude 계정과의 연결, 외부 AI 호출, 운영 HTTPS 배포는 환경 설정 후 검증해야 합니다. 웹훅 작업 큐와 저장소 단위 증분 동기화를 지원합니다. 저장소 안에서는 전체 PR·이슈를 재수집하며 항목 단위 증분 수집은 아직 지원하지 않습니다. 삭제되거나 권한이 사라진 원본의 캐시를 자동 제거하지 않으며 마지막 활동 시각과 동기화 오류를 함께 확인해야 합니다. 완료 후 YAML 변경·revert로 태스크를 자동 재개방하지 않습니다. 프로젝트 전체 완료 기준과 취소 정책의 추가 자동화는 후속 범위입니다.
